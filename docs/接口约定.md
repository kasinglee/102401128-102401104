# 数据接口约定（第一阶段定义，第二阶段沿用并补充页面接口）

以下 API 已实现于 `js/core.js` 和 `js/storage.js`。两文件在浏览器中作为普通脚本按顺序加载；Node 可用 `require()` 导入，便于最后编写单元测试。浏览器全局名称分别为 `LostFoundCore`、`LostFoundStorage`。

## 物品字段

```js
{
  id: "唯一编号", ownerId: "发布者在本浏览器的编号",
  type: "lost" | "found", name: "物品名称", location: "地点",
  date: "YYYY-MM-DD", time: "HH:mm", description: "补充描述",
  contact: "QQ 或校内账号", imageData: "可选的图片 data URL",
  status: "寻找中" | "招领中" | "已找回" | "已归还",
  createdAt: "ISO 发布时间"
}
```

演示物品的 `ownerId` 固定为 `demo`，不可在“我的发布”中修改。新发布物品的 `ownerId` 为当前浏览器生成的 `clientId`。这仅提供单浏览器的发布者区分，不是跨设备身份认证。

## 页面可调用的仓库接口

```js
const store = LostFoundStorage.createStore(window.localStorage);
store.getItems();                  // 所有物品的副本
store.list({ type: "all", query: "耳机", location: "东3" });
store.getItem("demo-earbuds");   // 找不到时为 null
store.getMyItems();                // 当前浏览器发布的信息
store.publish(draft);             // { item, errors, saved }；校验或保存失败不会新增
store.finish(id);                 // { items, item, error }；只有 ownerId 匹配才能结束
store.subscribe(() => { /* 重新渲染 */ });
store.reload();                   // 其他标签页修改 localStorage 后可调用
```

`list()` 默认把进行中的信息排在已结束信息之前，再按发布时间倒序；搜索范围包含名称、描述和地点。可传 `type: "lost"` 或 `"found"`、`ownerId`、`includeFinished: false`。纯逻辑函数可直接调用 `LostFoundCore.validateDraft()`、`listItems()`、`finishItem()` 等。

`js/app.js` 负责页面。空白 `detail`、`my-posts` 页面仍保留在 `js/app.js` 中作为兜底，第二阶段已在 `js/pages/search.js`、`js/pages/detail.js`、`js/pages/my-posts.js` 中用同名 `registerPage()` 覆盖，并在 `index.html` 中放在 `js/app.js` 之后加载：

```js
LostFoundApp.registerPage("search", {
  render(ctx) { return "<section>...</section>"; },
  mount(ctx) { /* 为本页绑定输入、按钮等事件 */ },
});
LostFoundApp.navigate("search", { query: "耳机" });
// 首页卡片已调用 navigate("detail", { itemId })；详情页还可从 ctx.params.from 取返回目标。
```

`ctx` 提供 `store`、`core`、`params`、`escapeHtml`、`navigate`、`showToast`、`refresh`，第二阶段又增加了两个共用渲染入口：

```js
ctx.cardHtml(item)   // 与首页完全相同的物品卡片 HTML，已内部转义，搜索结果和“我的发布”直接复用
ctx.iconFor(item)    // 没有图片时按名称推断的占位图标
```

`window.LostFoundApp` 上也挂了同样的 `cardHtml` / `iconFor`，方便不在 `render` 作用域内的代码使用。所有用户填写的文字插入 HTML 前应调用 `ctx.escapeHtml()`。不要另建一套物品数据。最终请在 Chrome 中以 `file://` 直接打开 `index.html` 验证。

## 第二阶段补充的导航约定

```js
LostFoundApp.navigate("search", { reset: true }); // 首页搜索入口使用，进入搜索页时清空上一次的搜索状态
LostFoundApp.navigate("search");                  // 不带 reset，保留搜索状态（详情返回搜索时走这条）
```

- `navigate()` 每次调用都会生成**新的** `params` 对象，而 `refresh()` / `store` 变化触发的重复渲染沿用同一个对象。`js/pages/search.js` 因此用 `ctx.params` 的对象身份判断“是否刚进入本页”：只有对象变了且带 `reset` 时才清空状态，重复渲染不会误清。
- 搜索的关键词、类型、地点和“是否已提交”保存在 `js/pages/search.js` 的模块作用域，所以从搜索结果进入详情再返回时，关键词、筛选条件和结果都保留。
- `navigate("detail", { itemId })` 会自动补上 `from: 当前页面`；详情页左上角返回读取 `ctx.params.from`，分别回到 `home`、`search` 或 `my-posts`。
- 关键词为空（含纯空格）时不执行检索，页面回到初始提示；`search.js` 在 `resultHtml()` 里也做了同样的兜底，避免输入被清空后重新渲染时列出全部记录。
